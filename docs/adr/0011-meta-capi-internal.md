# Internal Meta CAPI reuses the sGTM pixel-fed tag, deduped by the pixel's own event_id

We replace Meta's hosted server-side solution (sunsets **September 2026**) with our **own** Conversions API send by **reusing the paused Stape "Facebook Conversion API" tag** in the server container (`Facebook cAPI`, tag 15) rather than building a direct backend→Graph API service. The tag stays **browser-fed** (the sGTM GA4 client claims hits forwarded from the web GA4 tags). Dedup against the client-side pixel is made correct **by construction**: CAPI sends the value the pixel already emits as `eventID` (`{{dlv - ecommerce.transaction_id}}`) unchanged as `event_id`, paired with an `event_name` that **byte-matches the pixel string per conversion**. Customer `user_data` is assembled in a single server-side variable and hashed by the Stape tag. The send is gated on **per-vendor Meta consent** forwarded from the browser into sGTM.

This ADR records the **design**; the wiring reference lives in [`docs/gtm/facebook-tracking.md`](../gtm/facebook-tracking.md). Step 1 of the rollout (deactivate our prior sGTM CAPI) is **done** — tag 15 verified `paused` against live GTM on 2026-06-16.

## Considered Options

- **Transport — browser-fed sGTM, reuse the existing tag (chosen)** vs _backend-fed sGTM_ vs _direct backend→Graph API_. Reuse wins on time-to-deadline: Addingwell sGTM + the Stape tag already exist (tested, `testId TEST54905`), and this repo manages exactly these entities. The browser→sGTM hit is **first-party** (Addingwell domain), so it survives the adblockers that block `connect.facebook.net` — the common signal-loss case. **Boundary accepted:** browser-fed recovers events where the page loaded but the pixel was blocked; it does **not** recover bookings with no confirmation-page load (app abandon, email-only, server-confirmed) — only a backend-origin event would, and that is out of scope here.
- **`event_id` — reuse `ecommerce.transaction_id` on both sides (chosen)** vs _switch both sides to the `fct_order` booking UUID_ vs _block on a Snowflake check first_. Meta dedups only when `event_name` **and** `event_id` match. The pixel already sends `eventID = ecommerce.transaction_id`; sending the same value from CAPI makes parity hold regardless of what it maps to, eliminating the 2024/2025 **double-count** (CAPI + pixel counted twice because ids/names diverged). Whether `transaction_id == fct_order` UUID is an **analyst reconciliation** for Snowflake, decoupled from the send. `event_id` is **never hashed**.
- **`event_name` — byte-match the pixel per conversion (chosen)** vs _send the standard `Purchase`_ vs _standardize all conversions onto `Purchase`_. The pixel emits **custom** names: `Purchase` (Achat, tag 836), `GtmPurchase` (1096), `GtmTransaction` (1526). Sending `Purchase` for the `GtmTransaction` pilot — or the GA4 name `gtm_purchase`/`purchase` via `inheritEventName` — would mismatch and re-break dedup (names are case-sensitive). So CAPI sends the exact pixel string per conversion. This forces **one CAPI tag per conversion** with an explicit `event_name`, replacing the single inherit tag.
- **`external_id` — booking UUID (chosen by operator)** vs _stable `customer_uuid`_. Recorded with a caveat: `external_id` is an **identity / cross-event matching** signal, and a per-order UUID is unique on every event → it links nothing in Meta's graph → the matching work falls entirely on `em`/`ph`. A stable per-customer id exists (`dlv - customer_uuid`, #945) and would carry real matching value. Revisit if match quality underperforms.
- **PII assembly — one server-side `user_data` variable, Stape auto-hashes (chosen)** vs _pre-hash in the browser_ vs _loose per-field params mapped in the tag UI_. Single normalization+mapping point, hashing stays server-side, mirrors the existing `upd - customer_data` (Google Ads Enhanced Conversions) variable. No client/server hash-parity constraint exists because the **pixel sends no `em`/`ph` today**.
- **Consent — per-vendor Meta consent forwarded into sGTM (chosen)** vs _GTM consent mode_. The codebase gates per-vendor at the **trigger** level (`consentSettings` is `notSet` on every FB tag); consent mode is unused. We carry `didConsentToFacebook` (#909) on the GA4 hit and condition the CAPI tag's trigger on it — matching the existing pattern (e.g. trigger `purchase (consent Facebook)`).

## Consequences

- The single inherit-name tag 15 (trigger 14, `inheritEventName`) is superseded by **one explicit-`event_name` CAPI tag per conversion**, each on a trigger gated by `Client Name == GA4` **AND** `facebookEventFilter == true` **AND** `eventData - fb_consent == "true"`.
- The **web GA4 forward tags must newly carry** the customer fields (`customerEmail/PhoneNumber/FirstName/LastName` + city/country) and `fb_consent = {{JS - didConsentToFacebook}}` as event params, or sGTM has nothing to map.
- **No hashed PII leaves sGTM without Meta consent** — RGPD-clean, defense in depth on top of Meta's own consent handling.
- **Pre-live hygiene:** strip `testId TEST54905` + `logType: debug` from the CAPI tag before unpausing to production.
- **Rollout is staged:** pilot on `GtmTransaction` (unused in campaigns, safe) → verify dedup rate + volume in Events Manager → replicate verbatim on the campaign-critical `GtmPurchase`. The `Achat`/`GtmTransaction` conversions are safe to change; `GtmPurchase` is not.
- **Out of scope for this repo:** whether Meta's hosted solution stays active on `GtmPurchase` / off on the others lives in Meta Events Manager dataset settings, not GTM.
